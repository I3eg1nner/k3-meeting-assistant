# 发布保护与验证边界

`scripts/deploy-k3.sh` 先在开发机构建，上传到独立的 pending 目录。上传成功后才停止旧服务、保留旧代码目录并切换新版本。安装脚本显式重启服务，再分别验证无令牌请求被拒绝、有令牌请求健康正常；失败时恢复旧代码和旧 service unit，并重新启动原本处于运行状态的服务。previous/failed 目录保留以供排查，不自动删除。

生产 service 的配置文件为必需项，启动前要求非空访问令牌和明确的数据/静态资源绝对路径。现有 API 不变，令牌不会在健康检查输出中显示。

## 仍需真机验收

- 在现有 K3 上验证升级成功、上传中断、安装失败、启动失败和恢复旧版。仅本地脚本语法检查不代表这些情形已验收。
- 本方案回滚应用代码和 service unit，不回滚 apt 包、模型或数据库。未来出现不兼容数据库迁移时，必须先设计迁移/备份策略，不能直接依赖代码回滚。
- 仍使用 root，原因是 A100/TCM 及模型路径权限尚未在专用用户下验证；最小权限用户和 TLS 入口仍为发布前待完成项。
- Python 守护器按 0.2 秒采样内存，并终止自己创建的进程组及 Linux 上观测到的子进程。它不是内核硬内存隔离；短于采样间隔的峰值、首次采样前即脱离父进程的 daemon 仍需以 cgroup 限额补强。Linux 子进程树测试需在 K3/Linux 执行。
- 复用外部已有 llama 服务时，管理器不终止不属于自己的进程。外部服务的生命周期和内存硬限额应由其部署单元负责。
